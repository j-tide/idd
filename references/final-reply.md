# 最终回复模板

本轮开发或恢复执行结束时读取本文件。结论先行，使用下列固定顺序；按目标规模缩短内容，不重复粘贴执行日志。首次提请验收、同轮直通合入（此前未汇报过改动与验证）、部分完成或受阻时使用「标准模板」；**用户验收确认后仅执行准入合入（`idd land`）时改用「验收后准入回执（精简版）」**，避免复读已确认的完成内容与验证表格。纯咨询、只读评估或仅“聊想法建 Issue”不套用开发交付报告。

## 状态与表达

- **🔵 PR / MR 待验收 / CI 运行中**：本地 TASK、验证及最终 Review 已完成并已提交 PR / MR，等待远端 CI 结束或用户验收确认。
- **🟡 待本地验收**：（纯本地无 PR/MR 模式）必要 TASK、验证及最终 Review 均已完成，列出供用户验收的工作树、需求分支和提交 SHA。
- **✅ 已完成**：约定范围、必要验证、Review、CI 检查与用户验收均已满足，且已线性合入（说明工作树/分支保留或清理情况与 `TASK/` 清理结果）；验收后仅执行准入合入时，直接采用下方「验收后准入回执（精简版）」。
- **🟡 部分完成**：已有独立交付，但仍有必要任务或检查未完成；列明剩余范围。
- **⛔ 受阻**：关键条件未满足（含连续两轮 CI 修复失败），当前无法继续相关工作；给出解除条件和下一步。
- **⏸️ 已暂缓 / ⏹️ 已取消**：仅用于用户明确作出的决定，说明已有工作和保留事项。
- **⚠️**：标识待处理、跳过或限制；不能当成检查通过。失败明确写“失败”，不靠图标暗示。

emoji 用于结论与需要关注的位置，避免每个条目都装饰；图标旁保留明确文字。完成数只计 `done`，分母是本 Issue 任务总数，暂缓和取消单独说明。授权范围调整后的阶段交付也应链接仍未完成的原任务，不通过缩小分母制造全部完成。

## 标准模板

```markdown
**<状态图标与结论>｜<Issue 标题（如 [#42](<Issue URL>) 导出 CSV）>**

<一句话说明实际结果或行为变化> **任务：<done 数>/<总数>。**

**完成内容**

- <最重要的变化及其用途>
- <其他必要变化；通常 1～3 项即可>

**验证结果**

| 任务 | 验证目标 | 实际结果 |
| --- | --- | --- |
| <TASK-XX，可链接任务文件> | <测试文件/命令/人工检查> | <通过数，或失败/部分/未执行及原因> |

- Issue 级检查：<实际运行的回归、类型检查、构建、Lint 等及结果；不适用或跳过的检查说明原因>。
- Review：<完整 Issue Diff 的实际检查结果；有遗留问题则明确列出>。

**⚠️ 待处理事项**

- <阻塞、未完成或限制；下一步和解除条件。没有此类事项时省略整段>

**交付状态**

- **Issue**：[#编号](<Issue URL>)（纯本地无远端时省略） · <✅ 已关闭（验收 m/n） / 🔵 待验收（TASK done/total） / ⛔ 受阻（TASK done/total）>
- **PR / CI**：[PR #编号](<PR URL>) 或 [MR !编号](<MR URL>)（无则省略或写 `未创建`） · <✅ PR 已合入 · CI 通过 / ✅ CI 通过 · 待合入 / ⛔ CI 失败>
- **主线 / 分支**：`<main @ 短SHA>` 或 `<分支名>` · <✅ Squash 已同步（`TASK/` 已清理） / ⬆️ 已推送远端 / ⏳ 未合入>
- **工作树**：`<分支名>` 或 `<路径>` · <📁 已保留 / 📁 工作区干净 / 🗑️ 已清理>
```

「交付状态」统一采用以上 **紧凑单行列表**（每项 1 行：`• **环节**：<对象> · <状态>`），去废话，只保留当前阶段真正有信息量的 3～4 行（不再写“无 Merge 节点”、“如需释放空间可运行 `idd cleanup`”等冗余提示）。**关联的 Issue 和 PR / MR 有远端地址时，必须渲染为可点击 Markdown 链接（`[#编号](<Issue URL>)`、`[PR #编号](<PR URL>)` / `[MR !编号](<MR URL>)`），不要只写纯文本编号**：

- **✅ 已合入 main**（同轮开发直通合入）：`Issue`（`[#23](<Issue URL>) · ✅ 已关闭（验收 4/4）`）、`PR / CI`（`[PR #24](<PR URL>) · ✅ PR 已合入 · CI 通过`）、`主线`（`` `main` @ `8910e30` · ✅ Squash 已同步（`TASK/` 已清理） ``）、`工作树`（`` `feat/23-...` · 📁 已保留 `` 或 `🗑️ 已清理`）。
- **🔵 PR / MR 待验收**：`Issue`（`[#25](<Issue URL>) · 🔵 待验收（TASK 3/3）`）、`PR / CI`（`[PR #26](<PR URL>) · ✅ CI 通过 · 待合入`）、`分支`（`` `feat/25-...` · ⬆️ 已推送远端 ``）。
- **🟡 纯本地待验收**：`分支`（`` `fix/dark-flicker` @ `a1b2c3d` · 🟡 待本地验收（TASK 2/2） ``）、`工作树`（`` `../app-worktrees/...` · 📁 工作区干净 ``）、`主线`（`` `main` · ⏳ 未合入 ``）。

表格一行对应一个任务或一组共享验证的任务，保留任务到测试/检查的映射；不要逐个展开全部测试用例。长命令可在表中简写测试目标，并链接包含真实命令和结果的任务文件。小 Issue 可用一句话合并“完成内容”，仍保留进度、验证、必要限制和交付事实。

“全部任务记录为 done”不能单独证明 Issue 级检查通过。跳过全量产品测试时说明与本次改动范围的关系；没有执行构建不能写成构建通过。只做文档检查时写明实际检查，不编造测试数量。

本地提交、推送开发分支、创建 PR/MR、CI 通过、Squash 合入主线、清理工作树是不同事实，分别陈述。有 `origin` 远端时，向当前需求开发分支执行 `git push -u origin HEAD` 属于本轮常规交付步骤，不要因误解“外部操作”而跳过推送开发分支；不要把“已提交”写成“已合入”，也不要为了填齐交付状态而擅自执行合入 `main`、强推共享历史、发版或部署等未授权操作。链接应指向用户能访问的实际文件/产物；本地文件在回复中使用绝对路径。

## 验收后准入回执（精简版）

适用于用户已验收通过、本轮仅执行准入合入（`idd land` 或纯本地线性合入），且改动与验证此前已汇报（或用户已在 PR / MR 直接验收）的场景。同轮完成开发并按授权直通合入（此前从未汇报过改动与测试证据）时，仍使用上方「标准模板」。

**规则**：
- **省略「完成内容」「验证结果」以及「交付状态」小标题**，仅保留 1 行结论标题 + 紧凑 4 行状态（纯本地无 PR/MR 时 3 行）。
- **明确写清 PR / MR 已合入**：标题与 `PR / CI` 行均明确体现合入状态（GitHub 写 `PR 已合入`，GitLab 写 `MR 已合入`；若 `--auto` 仍在等待远端合入队列，如实写 `⏳ 自动合入排队中`，不得写成已合入）。
- **关联的 Issue 和 PR / MR 必须为可点击 Markdown 链接**（有远端地址时统一写成 `[#编号](<Issue URL>)`、`[PR #编号](<PR URL>)` / `[MR !编号](<MR URL>)`）。
- **仅在有额外动作或异常时追加 `⚠️ 说明`**：例如合入前触发 Rebase 解冲突并补跑复测（简述命令与结果）、`--auto` 仍在等待、本地主工作树 `main` 有未提交改动未能快进、`evidence/` 触发清理暂停等；一切顺利时不输出该段。

```markdown
**✅ PR 已合入 main｜[#27](https://github.com/owner/repo/issues/27) 新增直观原型对齐流程、本地预览与精简交付状态**

- **Issue**：[#27](https://github.com/owner/repo/issues/27) · ✅ 已关闭（验收 5/5）
- **PR / CI**：[PR #29](https://github.com/owner/repo/pull/29) · ✅ PR 已合入 · CI 通过
- **主线**：`main` @ `99559ff` · ✅ Squash 已同步（`TASK/` 已清理）
- **工作树**：`feat/27-visual-preview-and-reply` · 📁 已保留
```

GitLab 将 `PR` 替换为 `MR !编号`（如 `✅ MR 已合入 main`、`[MR !29](<MR URL>) · ✅ MR 已合入 · CI 通过`）；纯本地无 PR/MR 场景标题写 `**✅ 已合入 main｜<任务标题>**`，省略 `Issue` 与 `PR / CI` 行，保留目标分支/工作树与 `main` 提交 SHA。

## 受阻时的写法

例如连续两轮 CI 修复未通过或缺少真实联调凭据时，结论可写：

```markdown
**⛔ 受阻｜#44 飞书 Webhook 通知**

已完成适配器骨架与本地 Mock 回归，因缺少真实签名密钥无法完成线上联调校验。**任务：1/2。**

**验证结果**

| 任务 | 验证目标 | 实际结果 |
| --- | --- | --- |
| TASK-01 | 签名生成与本地单测 | 已通过；具体命令与证据见任务文件 |
| TASK-02 | 真实 Webhook 联调及 CI 集成测试 | 未执行/失败：缺少测试凭据；已按上限停止自动重试 |

- Issue 级检查：本地单测与 Lint 通过；端到端联调未完成。
- Review：已完成当前 Diff 核对，不能据此宣称真实渠道可用。

**⚠️ 待处理事项**

- 解除条件：提供测试环境 Webhook 地址与签名密钥后，通过 `idd start 44` 回到原工作树继续 `TASK-02`。

**交付状态**

- **Issue**：#44 · ⛔ 受阻（TASK 1/2）
- **PR / CI**：未创建
- **分支**：`feat/44-webhook` · ⬆️ 已推送 · 等待解除阻塞
```

示例数字只用于展示结构，实际回复必须替换成当前任务事实。用户偏好更精简或另有输出格式时，保留必要事实并遵从其明确要求。
