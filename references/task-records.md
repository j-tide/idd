# 任务记录约定

创建或实质修改任务文件时读取本文件。范围、验收、当前状态和实际验证以任务文件为准；提交与 PR 汇总保存历史，查询只派生视图。

## 任务模板

```markdown
# TASK-01：<任务标题>

- Issue: <42-export-csv 或 #42；纯本地未建 Issue 时写目录名或 none>
- Status: planned
- Depends on: none
- Test: <对应测试文件、已有测试目标，或不适合自动化的原因及替代检查>

## 任务范围
<包含和不包含的工作>

## 验收标准

- [ ] <可观察、可验证的结果>

## 实现注意事项

- <必要约束、已有实现、授权或兼容要求>

## 验证方式

- Command: <从实际配置确认的命令，或明确的人工操作步骤>
- Expected: <通过条件>

## 执行结果

- Outcome: pending
- Notes: 尚未执行。

### 当前阻塞

无。

### 验证记录

尚未执行，不预填通过记录。
```

实际发生验证后，用下表记录；相同操作可合并同一行，失败、跳过和后续成功分别保留。

| 日期 / 修订 | 命令或操作 | 实际结果 | 证据 |
| --- | --- | --- | --- |
| <日期、源码 SHA 或配置版本> | <实际命令或具体操作> | <passed/failed/partial/skipped；数量、错误或原因> | <任务内事实、仓库相对路径或持久产物标识> |

`Notes` 保持为当前结论的简短摘要。实现说明、Review、浏览器检查、集成和发布事实分别放在有标题的说明或验证表中，不新增同义的结果字段。命令含 `|` 时转义或改用列表以保持 Markdown 可读。需要时可自由补充说明，不要求把所有信息都结构化成字段。

## 状态与结果

### Status：任务生命周期

| 值 | 含义与使用条件 |
| --- | --- |
| `planned` | 已定义，尚未执行 |
| `in_progress` | 正在执行；依赖及授权满足 |
| `blocked` | 仍需完成，但当前有未解除的条件；必须有当前阻塞摘要 |
| `deferred` | 用户明确决定暂缓；记录决定、保留范围和恢复条件 |
| `cancelled` | 用户明确取消；保留取消原因和既有工作，不伪装成完成 |
| `done` | 本 TASK 的验收条件、必要验证与证据留存均满足。整个需求的用户验收另行确认 |

常规流转为 `planned → in_progress → done`；阻塞可从 `in_progress` 进入 `blocked`，解除条件后回到 `in_progress`。不得通过反复切换状态来清空同一问题的修复次数。暂缓/取消只按用户决定处理，部分成功保持实际未完成状态。

### Outcome：当前验证结论

| 值 | 含义 |
| --- | --- |
| `pending` | 尚未形成实际验证结论 |
| `passed` | 当前约定范围的全部必要检查通过 |
| `failed` | 必要检查存在已确认失败 |
| `partial` | 已有验证或完成子项，但仍缺必要验证/证据；不能整体通过 |
| `skipped` | 本次没有执行检查；必须记录原因，不代表通过 |

`Status` 与 `Outcome` 独立：代码检查全部通过但仍缺真实业务验收时，任务可为 `blocked`、Outcome 为 `partial`；用户暂缓前曾发生验证失败时可为 `deferred`、Outcome 为 `failed`。`done` 任务应为 `passed`，不能用跳过必要检查凑齐完成数。已明确不适用的检查记录为 `skipped` 并说明依据，不影响其他必要检查真实通过的结论。

对旧任务中的 `Outcome: done`、长段总结或其他历史写法，不批量替换，不倒推当时验证发生过。本轮触及该记录时，将原文保留为带日期的历史说明，再按可取回证据填写当前结论。未知状态不自动映射为完成。

## 证据留存

1. **任务内保留最低事实。** 写明执行日期、相关源码/配置/产物版本、实际命令或操作、结果与数量、错误类别及结论边界。浏览器和真实集成还需环境与关键操作，截图不能单独证明功能成功。已有自动化测试及其修订也要可定位。
2. **小型附件随 Git 留存。** 有必要长期保留的脱敏 JSON、日志摘要或截图放入 `TASK/<issue>/evidence/TASK-XX/`，随对应任务提交；任务文件链接到附件。不提交密钥、会话、原始个人数据、生产数据库备份或大体积临时产物。注意：合入 `main` 前执行 `idd land` 时若检测到 `evidence/` 含附件，会默认暂停提醒确认保留或使用持久化产物链接后再清理。
3. **大体积/外部证据使用持久产物。** 在任务中记录稳定地址或产物 ID、生成版本、访问方式及约定保留期限；对导出文件可附摘要校验值。访问受限需写明限制；短期 CI 下载链接不自动满足长期留存。没有持久服务时保留足够的脱敏摘录，不凭空假定外部平台会永久保留。
4. **忽略目录仅作临时空间。** `run/`、临时工作树和个人机器绝对路径不能作为结论的唯一长期依据。清理、迁移、结束任务前检查引用是否仍可访问，必要证据是否已转存或在任务中保留足够事实。任务目录的 `evidence/` 也要确认未被其他忽略规则排除。
5. **证据缺失如实处理。** 旧路径失效时标记“历史记录如此，但原始附件不可取回”，保留原引用，不重新制作附件冒充当时产物。只有当前可取回材料或新一次真实验证才能支撑对应结论；当前必要验收仍缺证据时保持未完成。

不要求留存每一段终端输出。可从源码和命令复现的自动化验证，通常保留命令、修订和结果即可；不能复现的人工/外部验收应留存足以复核结论的材料。复现会产生外部写入、付费调用、部署或生产操作时，不因需要补证据而越过原授权。

## 长期阻塞与恢复

处于 `blocked` 或 `deferred` 时，将下列摘要放在“执行结果”的验证历史之前：

```markdown
### 当前阻塞

- 更新于: <本次实际更新日期>
- 已完成: <已成立的子项及证据位置>
- 剩余项: <尚未满足的具体验收条件>
- 原因与影响: <外部条件/产品问题/待决策；受影响任务>
- 解除条件: <需要什么事实或决定，不写模糊的“继续观察”>
- 下一步: <可执行动作和责任方；需要用户动作时准确说明>
```

- 每次恢复先读摘要并检查条件是否变化；条件不变时，不重复要求已给出的凭据/授权，也不重复执行同一失败操作。保留两轮有针对性修复的上限，单纯恢复对话不重置次数。
- 当出现第二次恢复，或已有多个日期的尝试难以一眼判断剩余项时，整理为“当前摘要 + 按日期的历史尝试”；保留原始失败、实际操作和后续成功，避免 `Notes` 持续追加成长日志。摘要引用原验证表或历史分节，不复制整段历史。
- 子项可以独立验收或外部等待会遮蔽其余交付时，按下节拆为后续任务/独立目标；保留原验收项与承接链接，不重编号、不把剩余工作从统计中消失。
- 用户确认某个阶段独立交付时，明确该阶段的需求、分支和验收范围，关联剩余工作。未经明确范围调整，不能用已通过子项勾选整体标准或把 blocked 标为 done。缺少凭据的四家联调不能由其中一家成功替代。

## 范围增长与任务依赖

- 发现新范围先写原因、与原验收的关系、依赖和测试映射，再实施。仍服务同一交付结果且在已有授权内，可在原目录追加任务；需要独立交付、不同授权或无关能力时拆建新 Issue 并相互引用。
- 总量超过约 10 项、相对初始任务数明显增长（如翻倍），或同一验收连续追加前置修复时，触发一次范围复核。数量只提示复核，不强制拆分。记录“继续同一 Issue/分阶段/拆分新 Issue”的理由、当前验收边界、剩余项和授权是否覆盖。
- 追加任务使用下一个稳定编号。依赖按有向无环关系执行，不要求编号递增等于执行顺序；引用跨 Issue 任务时写全目录名。创建和调整时确认依赖存在且无环，不能让 cancelled/deferred 依赖悄悄视作完成。
- 已完成任务的新问题由新任务承接，引用原任务及复现证据。对未完成任务的范围调整应保留原要求和用户决定；转移验收项要给出承接位置，不能删掉难以完成的标准使旧目标看起来已完成。
- 对明显超出当前授权的工作，先准备可评估的范围和影响再询问必要决定；用户已明确授权的普通任务自动继续。

## 事后补录

补录是整理事实，不会使原开发追溯性地符合流程。遵循适用的项目约定，保留真实记录和历史来源。

1. 检查当前工作区、提交和原任务记录，确定补录范围并保护无关改动。新建本轮整理目录；若只补已有任务的一段说明，明确标注本轮补录并保留原文。不要把新增的计划写成当年的事前计划。
2. 在任务中显式写明：“原开发没有预先按 IDD/TaskFlow 完成任务定义/验证记录/逐项提交中的哪些步骤；本节为事后补录。”有何证据只记录何证据，不一概断言所有历史环节缺失。
3. 分开列出历史实现、历史验证和本轮实际验证。历史记录写来源（原提交 SHA、原任务、产物）、原日期和可取回性；未经本轮重跑的历史通过数不得写成本轮测试结果。确实无法恢复的材料明确标记缺失。
4. 本轮能安全运行的检查实际运行并记录新日期/修订；涉及外部写入、模型调用、通知、部署或生产迁移时，另查已有授权，不能为了补录自行重演。
5. 在本轮需求分支逐 TASK 提交补录或实际修复。保留旧提交和原日期，测试结果注明实际来源。补录需求也在用户验收后按[Issue 与 Git 协作流](git-issue-workflow.md)交付。

补录整理完成不代表原功能、真实联调、推送或部署已完成；它们继续沿用各自的事实和剩余条件。
